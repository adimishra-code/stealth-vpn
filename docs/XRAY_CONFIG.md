# StealthVPN — Xray Configuration & REALITY Key Management

## Overview

Xray-core is deployed on every VPN edge node to provide VLESS + XTLS-Reality +
Vision flow cloaking. This document explains the config, REALITY key lifecycle,
and how the backend injects users into the running Xray instance.

### Key Components

| Element | Purpose |
|---------|---------|
| `inbounds[0]` | VLESS + REALITY listener on port 443. Accepts cloaked client connections. |
| `inbounds[1]` | Xray API (`dokodemo-door`), bound to localhost:10085. Used to add/remove users dynamically. |
| `api` service | Enables `HandlerService` (user management) and `StatsService` (bandwidth tracking). |
| `fallbacks` | If a non-VLESS probe hits port 443, forward to Nginx on port 80. |
| `routing` | Routes API traffic internally. Blocks private IP probes. Blocks geoip:private LAN traffic reaches `freedom` outbound (not `block`), but private IP routing gap was fixed in the actual config generated by `provision-node.sh`. |
| `sniffing: false` | Disable content sniffing — unnecessary overhead for tunnel traffic. |
| `policy.levels.0` | Enables per-user uplink/downlink stats. |

## REALITY Key Generation

### On the VPN node

```bash
# Generate X25519 keypair
xray x25519

# Output:
# Private key: <64-char base64>
# Public key:  <44-char base64>

# Generate shortId (8 bytes = 16 hex chars)
openssl rand -hex 8
```

**Store the private key** — it must be in `realitySettings.privateKey` in the server config.
**Store the public key** — the client needs it in their outbound config.
**Store the shortId** — both server and client need matching shortIds.

## User Provisioning via Xray API

The backend SSHes into the node and calls the Xray API on `127.0.0.1:10085`.
This is the **only** way users are added — no config file editing or Xray restarts.

### Add User

```bash
xray api adduser \
  --server=127.0.0.1:10085 \
  --email="${UUID}@stealth" \
  --uuid="${UUID}" \
  --flow="xtls-rprx-vision" \
  --level=0
```

The email field is used as an identifier for the user. The backend uses the UUID
as the email prefix so each user is uniquely identifiable.

### Remove User

```bash
xray api removeuser \
  --server=127.0.0.1:10085 \
  --email="${UUID}@stealth"
```

### Query Users

```bash
xray api query \
  --server=127.0.0.1:10085
```

### Query User Traffic

```bash
xray api query \
  --server=127.0.0.1:10085 \
  -pattern="${UUID}" \
  -reset=false
```

## Why XTLS-Reality + Vision Beats ML DPI

### The GFW ML Problem (2026)

GFW extracts 40+ statistical features per TCP/UDP flow:
- Packet size distribution (mean, stddev, entropy)
- Inter-packet delay histogram
- Burst patterns (packets/second in sliding windows)
- Uplink/downlink byte ratio over time
- Handshake entropy (initial 4-packet signature)

These are fed into random forest classifiers trained on millions of labeled flows.
By late 2025, GFW could distinguish vanilla WG-in-TLS from real HTTPS with >92% accuracy.

### How Reality Defeats It

1. **Handshake Spoofing**: The TLS 1.3 ClientHello is indistinguishable from a
   real connection to `microsoft.com`, because it *is* a real connection to
   Microsoft's certificate. Active probers get forwarded to the real site.
   No self-signed or CA cert to flag.

2. **serverNames**: Using `microsoft.com` — a conn defined, high-reputation
   domain. Never use your own domain; active probers scan for mismatches.

3. **Vision Flow Control**: Standard XTLS strips the outer TLS header and
   forwards the inner TLS directly. Without Vision, the resulting stream has
   a characteristic packet size ladder (length field + header + payload) that
   ML classifiers learned to flag. Vision pads and fragments the inner TLS
   record to eliminate this size-based fingerprint.

4. **No static cert**: The handshake uses the REALITY dest's actual cert.
   Rotating the dest domain (between microsoft.com, apple.com, cloudflare.com)
   further complicates ML fingerprinting.

5. **fingerprint: chrome**: The TLS fingerprint matches Chromium's TLS stack
   exactly. Most browsers use Chrome's BoringSSL. Firefox has a different
   fingerprint and is rare enough to flag.

## Security Note

**The Xray API SHA on port 10085 runs ANY** — anyone on the machine can add users.
Clamp to localhost via firewalled localhost uid. Restrict UFW to explicitly block
inbound to port 10085 on `eth0`, `ens3`, etc.
